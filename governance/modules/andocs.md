## Document scope and prompt construction

For document work, identify `document_kind` as `paper_draft`, `analysis_note`, `cross_document_audit`, or `object_review` when applicable. Declare `primary_target_repo`, exact `repo_locations`, `allowed_to_modify` and `read_only` scopes, the other document repository's disposition, source and validation state, and `reference_material_to_read` when used. `paper_draft` covers paper text, title/abstract, figures/tables, bibliography, supplements and builds; `analysis_note` covers AN text, appendices, comments, replies and builds. `cross_document_audit` is read-only unless a separate round authorizes edits in each independent repository. `object_review` covers questionnaire/reviewer evidence and paste-ready answers, not a shortcut to implementation changes.

The prompt must declare both root `validation_ceiling`, using only root `AGENTS.md` values, and a separate `document_validation_level` describing the intended document evidence. The closed document levels and compatible root ceilings are:

| `document_validation_level` | Required root `validation_ceiling` |
|---|---|
| `source_only` | `static_inspection_only` |
| `latex_compile` | `workflow_dry_run_or_config_validation` |
| `rendered_pdf` | `workflow_dry_run_or_config_validation` |

The document level does not authorize execution. For `latex_compile` or `rendered_pdf`, the prompt must separately satisfy applicable root command, output, side-effect and permission contracts and use the maintained repository-supported document build/render path. A document build or PDF inspection requires the needed command/output permission under root governance. Figure, table, datacard, limit, or other analysis-output regeneration is a separate domain-specific side effect requiring explicit authorization from its semantic owner; it is not a document-validation level or a document-governance task. Prompt fields for source/render checks include the affected active TeX graph, labels, references, citations, graphics and generated PDF binding only when relevant. Record validation start state and final state; changed source or outputs after validation invalidate claims bound to the prior state. User-run builds/regeneration remain user-supplied runtime evidence until their artifacts are inspected; an interruption with uncertain effects requires fresh state readback before retry.

## Document evidence and claim ceilings

Keep document validation, separately owned analysis-output regeneration, human physics review, and collaboration/approval review distinct. Within document validation, static source inspection, repository-supported LaTeX compile with log audit, and rendered-PDF check establish different evidence. `compile_passed` does not prove a rendered check; a rendered check does not establish physics approval; physics review does not establish collaboration approval. Source, tests, and payload availability are not by themselves production behavior. For consequential implementation claims, record the evidence class and production-binding class (`production_bound`, user-authoritative production input, current source only, payload capability only, historical source only, or unresolved). The authoritative production input and production-bound configuration/output take precedence for production claims; current AN, implementation, tests and history have their narrower roles. Missing binding stays explicit.

For an active TeX change, inspect reachable `\input`, `\include`, `\subfile`, bibliography, graphics, labels, references and citations as material. Check duplicate keys/labels and missing active graphics when relevant. The supported entry point for each document is its tracked `source compile.sh` wrapper, verified at the live repository state. The AN wrapper uses `tdr --style=an b AN-24-174`; the paper wrapper uses `tdr --style=paper b TOP-26-006` and its guarded CMS TeX Live setup. The exact executable/CVMFS paths belong to the live native wrappers. Inspect TeX/BibTeX passes, filtered errors and the produced PDF path; a successful wrapper exit alone is insufficient. Do not use system TeX to bypass either wrapper or repeat accepted build discovery unless build inputs/configuration changed. A rendered check must inspect the relevant PDF content and bind it to the validated source state. Generated figures, tables, PDFs, logs or analysis outputs must identify provenance and whether regenerated; ordinary build and analysis-output regeneration are separate permissions and evidence levels.

Document evidence comparisons must match semantic stage, active source/reachability, numerical normalization, relevant bins/categories and consumer meaning. A diagnostic aggregate is not automatically the object consumed by a fit, figure or table. Use formal pull/significance wording only when the necessary statistical model and covariance are established. A resource or representation failure is a limitation, not permission to silently change targets, stages or tolerances. Imported runtime or implementation evidence cannot lift a document claim above its directly supported scientific ceiling.

## Reference material and cross-document boundaries

Workspace reference material is external to the paper/AN Git histories and remains read-only unless separately authorized. Name each in-scope document, source/origin, retrieval date, version when known, SHA-256, PDF and extraction path, and access limits. Extracted UTF-8 text is a search aid; consult the original PDF for ambiguous wording, tables, symbols or layout. Do not copy restricted CMS guidelines into document repositories or quote internal guidance extensively in reviewer-facing prose. Access to publication guidance does not imply figure-guideline review.

For a cross-document decision, declare `source_document`, `target_document`, `comparison_scope`, `authority_contract`, `mechanical_consistency_question`, and `physics_judgment_boundary`. The AN may own analysis selection/method when established; the paper owns its narrative and compression; official CMS wording comes from declared official reference material; numerical results require an explicitly identified current result source. Do not assume the AN wins every disagreement. Classify mechanical, wording and numerical consistency separately and leave uncertain scientific authority for the responsible human/native owner. Cross-document audit never merges Git histories or authorizes editing both documents.

## Object review and external evidence

An object-review prompt must identify the actual live questionnaire/checklist by path, title, revision and SHA-256, plus a distinguishing question. Instructions or recommendations alone are not the form. Preserve the form's section/question order, checkbox wording, tables, conditional sections and answer fields. Classify fields as fillable now, fillable with explanation, requiring bounded technical check, requiring user input, or inapplicable. Every material clause of a joined checkbox needs evidence; leave a partly supported broad checkbox unchecked and explain why. A complete user revision becomes the writing baseline; preserve its edits except for a verified conflict with evidence, a settled user decision, form structure, or an absolute safety rule, and report each deliberate deviation.

Keep a paste-ready reviewer answer separate from internal matrices, hashes, provenance, and follow-up registers. Reviewer-facing current documentation uses a maintained stable link; historical claims use immutable refs; production implementation uses a production-bound ref when available. Reviewer-facing answers avoid local paths, internal status labels and unnecessary Git archaeology. Distinguish fully data-driven yields from data-calibrated simulation, simulation without data calibration, and a model-constrained prediction. Distinguish global veto, category-specific veto and overlap removal. An object-cleaning claim needs the source/target collections, selection levels, ordering, direction, `delta_r`, affected categories and systematic-migration possibility, established from the actual consumer behavior.

For consequential evidence imported from an autonomous workstream, identify its checkpoint and evidence locator, direct source/runtime identity, invalidation conditions, supported claim ceiling, and any contradiction with canonical document state. A checkpoint is context/evidence, not task authorization or an automatic replacement for local scientific decisions. Source workstreams own implementation/runtime facts; ANDOCS/native document owners own AN/paper wording and document review; POG/reviewer bodies own their scientific policy. Current branch, HEAD, remote, CI, process and storage state require fresh readback when material. Preserve bidirectional handoff of accepted external evidence and canonical document decisions without copying mutable external truth into a new registry. `implemented`, `bounded_real_input_validated`, `production_bound`, `documented` and `reviewer_closed` do not imply one another.

## Document reviewer prose

Root `CONTRIBUTING.md` controls common reviewer-facing format and honesty. For an AN review, identify the relevant section/appendix, comment/reply consistency, source/build/render distinction, and any remaining human approval question. For the paper, identify text, figures/tables, bibliography, supplementary or template changes, whether numbers/plots were regenerated, and AN-to-paper alignment without claiming physics approval from wording alignment. Paper and AN changes normally receive separate commits, patches and review material; state dependencies and merge order instead of conflating histories.

Reviewer material for object review preserves live form structure and explains partial compliance in plain language. Distinguish source, build-log, rendered-PDF, production, human-physics and approval evidence in claims. State honestly whether CI was inspected, whether a user performed an action, and whether output was regenerated. Generated binaries and vendored LaTeX assets require provenance, version/authority and review implications when changed. Scientific wording changes need affected years, categories, processes, nominal/systematic behavior, validation and remaining human review. No document-specific rule here transfers scientific-content ownership to project governance.
