## Frame and dispatch one decision

Begin with a falsifiable decision question: what observed fact would make the task complete or stop it? Identify the semantic owner, exact repository and paths, an explicit `allowed_to_modify` set and `read_only` set, evidence to collect, validation ceiling, and any side effects. An investigation asks for evidence and a verdict without tracked edits. A documentation or coding task may edit within its grant and normally ends in a prompt-local commit. A validation task checks an established change without changing it. Other live modes own commit preparation, local integration, branch maintenance, publication, and production. Consult the live contracts instead of copying a closed mode or field table from this guide.

When one decision needs ordered activities with distinct effects, declare an `orchestrated_workflow`: each stage keeps its own mode, permissions, preconditions, serialized evidence, acceptance gate, and stop behavior. A later stage reads back earlier observed output; a planned value or an author's success label is not evidence. If a gate fails, is indeterminate, or reveals a new substantive choice, preserve completed effects and stop. The workflow does not invent a repair loop or borrow a permission from another stage. [CPC prompt construction](../../CPC.md) covers the governed dispatch; the [prompt-contract skill](../../.agents/skills/correction-lib-prompt-contract/SKILL.md) can lint supplied prompt text mechanically but cannot certify governance or authorize execution.

Before mutation, inspect the selected repository's live Git root, branch, HEAD, task-path/index dirt, applicable feature branches, and output collisions. The declared validation ceiling limits checks; a higher ceiling alone does not authorize a workflow, environment change, or production command. Available filesystem access, credentials, network connectivity, and executables are capabilities, not grants. Network reads, pushes, PR/MR writes, merges, and remote deletion each need their own explicit permission. A foreign dirty change is preserved and excluded; an exact authorized change is staged and reopened before commit. [Root Git policy](../../AGENTS.md) controls the details.

## Branches and local integration

Choose a development branch by **reuse-first applicability**: use fresh refs and semantic/dependency continuity to decide whether an existing active feature carries work this task needs. One applicable feature is normally continued; ambiguity or multiple applicable features require reconciliation; only a positive zero-applicable finding supports creating a new feature from the declared reference. Branch names and old reports alone cannot prove applicability. A reference or integration branch is a non-development surface; do not place new development commits there merely because it is checked out.

For a separately authorized local integration, prove source and target identities, ancestry, and clean switch conditions, then perform the declared method. The default is `ff_only`, which advances the local target without a merge commit. Read back both refs and the worktree afterward. It grants no push or remote merge. For `topeft` specifically, the live [`topeft` module](../../governance/modules/topeft.md) names `run3_test_mmerged` as its permanent integration branch, `run3_test_mmerged_anpicci` as its permanent personal reference branch, and `te/*` as feature development. Even a cumulative `te/*` branch remains a feature for the applicability gate. Those names and roles do not transfer to TOP26006_fw `master`, ANDOCS, or another repository. PR publication, remote merge, remote branch deletion, and history maintenance each require their own action-specific decision and authorization.

## Evidence, review, and handoff

Collect direct observations first: exact source or artifact identity, command and output, affected paths, and limits. Serialize them in the required report, patch, and only useful bounded diagnostics. Reopen the evidence, independently recompute material checks, then classify findings and derive a verdict. A test, generated package, filename, branch name, or agent-authored statement does not certify its own claim. A separate readback review can challenge coverage, links, source alignment, and provenance; it is still an agent review, not a substitute for a human scientific or publication approval.

For integration or other publication-grade sign-off, use the live [`AGENTS.md` review contract](../../AGENTS.md) to report confirmed blockers, additional unresolved risks, not-yet-evaluated surfaces, items closed with evidence, and confidence in completeness. Name exact identities when branch membership matters. An evidence package needs a traceable producer, source identities, manifest or declared contents, and an independent review boundary. The [evidence-package-review skill](../../.agents/skills/correction-lib-codex-evidence-package-review/SKILL.md) can compare a supplied local carrier to a reviewer-owned manifest inertly; it does not execute contents or authorize fixes or publication. A checkpoint passes accepted findings and invalidation conditions to the next task, while volatile Git, remote, storage, or process state must be read afresh when decision-material.

Production and publication are distinct from implementation validation. If an accepted plan calls for user-run production, the [manual-production-handoff skill](../../.agents/skills/correction-lib-manual-production-handoff/SKILL.md) can prepare a non-executing runbook with exact commands, collisions, logs, resume boundaries, and evidence to return. The user executes under separate authorization; output existence alone does not certify completion. No PKL or other production campaign is automatically authorized for Codex. Remote publication requires its own live remote readback and explicit remote grants.

## Reuse capabilities without moving ownership

Before writing a new helper, find an applicable maintained owner. Reuse it, compose or configure it, then consider a small compatible extension before a new reusable capability. A one-off extraction or comparison may remain an `EPHEMERAL_DIAGNOSTIC` in an authorized diagnostics area. A reusable runner, converter, manifest generator, or validator needs a maintained home, interface, failure and output contract, tests, and documentation. Do not leave recurring infrastructure in diagnostics by accident. See the live [`AGENTS.md` capability lifecycle](../../AGENTS.md).

For temporary payloads used by diagnostics, follow the [temporary filesystem hygiene rules](../../AGENTS.md#temporary-filesystem-hygiene), including private round-owned storage and exact-path disposition; recovery of prior-round remnants requires separate authorization.

The project-local skills have narrow jobs: the [prompt-contract skill](../../.agents/skills/correction-lib-prompt-contract/SKILL.md) helps draft or lint a prompt; the [diagnostics-execution-copy skill](../../.agents/skills/correction-lib-diagnostics-execution-copy/SKILL.md) copies explicitly selected, hash-checked UTF-8 files for later inspection but never executes them; the [evidence-package-review skill](../../.agents/skills/correction-lib-codex-evidence-package-review/SKILL.md) reviews an explicitly supplied carrier against an external manifest without running it; and the [manual-production-handoff skill](../../.agents/skills/correction-lib-manual-production-handoff/SKILL.md) renders a user-run plan without running or monitoring production. Use a skill only when its purpose fits the authorized task; its availability is not a permission grant. Read its live `SKILL.md` before use.
