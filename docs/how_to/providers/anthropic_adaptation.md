# Adapt the workflow to Claude Code

**How-to; official documentation reviewed 2026-10-23.**

> **Documentation status:** Official-provider mechanisms reviewed and mapped.
>
> **TOP26006_fw local Claude Code runtime:** **NOT LOCALLY TESTED / NOT QUALIFIED.**

Use the [provider adaptation worksheet](../adapt_to_another_ai_provider.md) for an exact version, surface, and installation. The mapping below describes current official Claude Code documentation. It adds no Claude launcher, settings, hook, runtime adapter, or claim that this checkout runs on Claude Code.

1. **Resolve instruction loading.** Claude Code's [memory and project-instruction guide](https://code.claude.com/docs/en/memory) describes `CLAUDE.md`, `.claude/CLAUDE.md`, and `CLAUDE.local.md`. These can alter default selection of `AGENTS.md`. Direct `AGENTS.md` reading is documented from **Claude Code v2.1.277**, subject to version and session conditions. The current Project instructions choices are `claude-md-or-agents-md`, `claude-md-and-agents-md`, `claude-md`, and `managed-only`. The default `or` mode reads `AGENTS.md` only under its stated `CLAUDE.md` conditions; a private `CLAUDE.local.md` can change that outcome. Check the actual setting and loaded files in the intended session.
2. **Inspect ancestors and descendants.** The guide describes ancestor instruction files, descendant `CLAUDE.md` and `AGENTS.md` loading as work reaches subdirectories, and `.claude/rules/` path-scoped rules that load on demand. The exact loading path depends on instruction mode and file/tool access. Record imports, exclusions and the observed chain rather than assuming that a root file governs every action.
3. **Map permissions on Claude's terms.** [Permission rules](https://code.claude.com/docs/en/permissions) and [permission modes](https://code.claude.com/docs/en/permission-modes) govern tool actions. Current documented modes include `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, and `bypassPermissions`; defaults vary by version and surface. Inspect the effective allow/ask/deny rules and [settings sources and precedence](https://code.claude.com/docs/en/settings), including user, project, local, managed, and session settings. Do not translate a Codex `approval_policy` label into a Claude mode by name.
4. **Trace each access surface.** The [Claude Bash sandbox guide](https://code.claude.com/docs/en/sandboxing) scopes its operating-system boundary to shell commands and children when enabled. Built-in file tools, web tools, hooks, and MCP paths need their own permission and isolation analysis; the Bash sandbox alone does not cover them. Determine the actual filesystem and network reach of each path and the behavior of unsandboxed retries or exclusions in the selected installation.
5. **Handle continuity, hooks, and review.** Inspect the [session](https://code.claude.com/docs/en/sessions) and memory behavior that applies to the chosen surface. [Hooks](https://code.claude.com/docs/en/hooks-guide) can automate or block actions, but they are action controls, not project authority or scientific acceptance. Preserve a project evidence record and separate reviewer even if a provider offers its own action or code review.
6. **Qualify only the exact proposed deployment.** Check the installed version, effective instruction mode, loaded ancestor/nested files, settings precedence, tool permissions, sandbox coverage, network and connector paths, evidence capture, and stop behavior with bounded harmless probes. Until that work is done, label a TOP26006_fw Claude runtime **not locally tested**.

The critical distinctions are: **`AGENTS.md` support is not Codex-equivalent `AGENTS.md` behavior; the same instructions do not imply the same permissions; the same prompt does not imply the same sandbox; provider action review is not project evidence review; and provider review is not owner acceptance.** See the [compatibility matrix](../../reference/provider_compatibility.md) for the documentary state of each mechanism.
