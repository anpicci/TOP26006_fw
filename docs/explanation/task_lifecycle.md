# The task lifecycle

A task begins with the result that would close its question. The responsible decision-maker identifies that result, its dependencies, permitted effects, needed evidence, and final acceptance boundary. The executable task then binds exact repositories, paths, inputs, revisions, validation limits, and stop conditions. Completion by an executor produces a result and provenance; review challenges the claim; acceptance remains a separate decision.

The smallest execution model that can produce that result is usually clearest. A short, tightly coupled task can stay serial in one repository. Multiple dependent steps can share one decision when each has a defined objective gate and only its own explicit permissions. Parallel work is useful for genuinely separable responsibilities with an explicit join and interaction review. Coordination across repositories is needed only when the result crosses their independent authority or compatibility boundaries. None of these choices grants an effect by itself.

The lifecycle can continue without repeating valid work. Accepted evidence remains usable while its identity, inputs, assumptions, and relevant interfaces still hold. A changed dependency calls for review of that dependency and directly coupled interactions. A bounded local repair preserves unaffected valid results and repeats the affected check. If a new choice or unsafe uncertainty appears, record the direct state and stop only the dependent action; independent authorized work may continue. Requirements for a later phase do not automatically block a correct current result.

When temporary task-owned state is to be retired, preserve portable results and evidence first, then apply only the authorized retirement after its gates.
