# Multi-repository research

Repositories may own different parts of one result: analysis, methods, documentation, or evidence. Each keeps its own history and rules. For a dependent task, identify the exact base and candidate revisions for each repository and who decides whether to use its result. The [repository registry](../../governance/repositories.md) describes durable roles; a local path or checked-out branch does not authorize a change in another repository.

A single repository and a serial sequence are sufficient for many tasks. Work across repositories is useful when the result actually depends on changes or evidence in more than one of them. A producer first supplies an identified result with its inputs, assumptions, and review; a consumer then uses that result under its own authorization. The [two-repository tutorial](../tutorials/07_coordinate_a_multi_repository_change.md) illustrates a serial transfer. Parallel work is useful only for separable responsibilities with explicit joins and review of their interactions; the [advanced coordination route](../advanced/index.md) covers that case.

Evidence can cross from repository A to repository B; authority does not migrate with it. Record what each artifact supports, its limits, and its provider-local review and acceptance status. B may reuse valid accepted evidence, but still needs its own permission to act, checks at the affected consumer interface, and responsible-human acceptance. A provider PASS cannot establish consumer compatibility or scientific validity; a consumer readback does not retroactively validate a provider change. The [handoff template](../../templates/handoff.md) records unresolved checks, invalidation triggers, and accepted work that should not be repeated without invalidation.

For a dependent change, bind the exact base and candidate revision in each participating repository. Follow the producer-to-consumer dependency direction, advancing each repository only when its own authorization and validation permit it. When compatibility depends on more than one repository, validate the exact set of revisions the consumer will use together at the affected interface. Separate histories mean there is no single global Git transaction. If a later step stops, preserve valid earlier results and report the partial state; a failure does not trigger automatic rollback of those results.

A temporary worker result is a frozen result and its evidence, not a permanent development branch. Preserve its portable result, base, inputs, assumptions, interfaces, and review before any destructive removal. Remove only the exact temporary paths or refs created for this task and authorized for removal, after the applicable validation checks. Permanent development state and unrelated changes stay protected. After removal, read back the final state to check that the intended temporary files or refs are gone and unrelated state remains intact.

These repository and workflow checks establish provenance and coordination limits. They do not by themselves certify scientific meaning, application behavior, affected consumer compatibility, tests, or runtime behavior; each task needs the relevant validation at its own boundary. The [review guide](../how_to/review_returned_evidence.md) describes how to check a returned result.

Automated workflow compilation is not part of the current documented model.
