# Model selection — common candidate guide v0.2.0

**Inactive design.** This guide proposes shared selection responsibilities and
criteria, not provider vocabulary, a ranking or an effect grant. It accompanies
[direct prompt authoring v0.3.0](direct_prompt_authoring_v0.md). The future
common policy owner is project governance through model_policy; native guides
own provider-specific options. Adoption must establish the maintained homes
without copying complete routing tables between documents.

The author selects and communicates a complete concrete configuration for each run
in the same self-contained delivery as the reusable task, outside explicit task
byte boundaries under CPC’s proposed construction rule. No necessary profile or
approval is deferred to chat; the existing report retains the delivered contents.
The executor applies it and records what was supplied and observable; the
reviewer challenges evidence and limits. One immutable attempt references exact
task bytes/revision, retained input/method contents and fixed criteria. Ordinary
model/reasoning changes create another author-selected run, not another task.
Required independent review and delegation permissions stay in the mandate.
A model explicitly studied as a scientific object stays a task constraint.

| Criterion | Question for the author / evidence consumer |
| --- | --- |
| Question and expected result | What decision/deliverable must this task support, under whose acceptance? |
| Difficulty and ambiguity | Is procedure fixed or does the task require synthesis, uncertain interfaces or adversarial reasoning? |
| Capabilities and tools | Which modalities, context, tools and surface controls are actually needed and documented for this product? |
| Verifiability | Can checks expose mistakes; what remains dependent on judgment or unavailable evidence? |
| Correction cost | What would an error or missed boundary require to repair, and can the result be reviewed before effects? |
| Resources and time | What latency, usage, monetary/resource limits and deadlines matter for this attempt? Use observed/official facts when needed, no invented prices or caps. |
| Reproducibility | Can another author recover task/input/method bytes, criteria, selected profile, guide version and observation limits? |

Select a proportionate, explainable configuration directly. There is no duty
to try models from cheapest to strongest, no automatic escalation, consensus
rule or universal second model. Missing data/permissions, unresolved target
ownership or an unknown external outcome must be addressed at that boundary;
a stronger model cannot supply them. A changed profile grants no upload,
retry, production, additional delegation or scientific decision.

Separate fixed preparation/maintenance costs (acquiring/reviewing/updating a
guide, installation profile or optional reusable method) from per-task costs
(mandate, input binding, graph and criteria) and per-run costs (selection,
configuration, execution where authorized, preservation, observation and
review/report). Loading a guide is not free. Repeated attempts on the same
task are not independent scientific task populations. Do not claim savings
from label counts or amortize unmeasured costs into an empirical result.

Retain task reference, provider/product, concrete native model/reasoning,
author rationale and guide revision/content locator as configuration data in
the existing report. Evidence separately records requested/dispatched values,
directly selected/runtime-reported values with their sources, or not_observable,
outputs and limitations. An unresolved guide/version limits reproduction of
the selection. Unavailable model or observed mismatch stops that attempt for
new author selection/dispatch, without silent fallback or overwritten evidence.

For a controlled comparison fix task bytes, actual inputs, method version and
parameters/conventions/denominators, scope, permissions and criteria. Record
uncontrolled environment, context, ordering, caches and stochastic variation.
If both model and effort change, compare the pair. Input or denominator changes
must not be attributed to the model. Qualification needs actual consumer
evidence under separate authorization; static identity is insufficient.

[OpenAI](providers/openai_selection_v0.md) is the first concrete guide. Add a
provider only when needed: identify responsible author/governance owner,
native product/model/options/tools, dated primary sources, limits, selection
examples and observation requirements. Map responsibilities rather than option
names. Do not presume equivalent reasoning scales, accessibility or controls,
create empty stubs or maintain a document per model. Vendor guidance describes
mechanisms; local adoption and observed availability remain separate evidence.
