# Glossary

| Term | Meaning |
| --- | --- |
| Research question | The claim or uncertainty a study seeks to address. |
| Method | The stated procedure and assumptions connecting data to a result. |
| Provenance | Where data, code, and observations came from. |
| Reproducibility | Ability to rerun a declared calculation with identified inputs and environment. |
| Validation evidence | Observations that check a bounded claim, with known limits. |
| Independent review | A check separate from executor self-report. |
| Accepted result | A conclusion adopted by the responsible scientific or project authority. |
| Project identity | The governed project name, here `TOP26006_fw`. |
| Checkout name | Any local directory name chosen for a copy of the project. |
| `repository_id` | Stable registry identity for a separate repository. |
| Local path | This installation's filesystem location for a repository. |
| Remote alias | Local Git name such as `origin`; not a URL or proof of remote state. |
| Branch role | Governance meaning of a branch, separate from its spelling. |
| Current ref | Freshly observed branch or detached HEAD and commit, not registry text. |
| Local profile | Ignored YAML carrying installation facts only. |
| Provider | The product or service chosen for AI assistance; its name does not assign project authority. |
| Research responsibility | A role in framing a question, producing evidence, reviewing it, or accepting a result, independent of provider branding. |
| Provider mechanism | A product-specific way to load instructions, control actions, access tools, or preserve context. |
| Documented compatibility | An official description of a comparable mechanism; it does not show that this project tested that mechanism locally. |
| Local runtime qualification | Bounded observation of the selected provider version, surface, settings, access paths, and evidence behavior in the intended installation. |
| Reference deployment | A dated worked example mapping generic method and governance concepts to one project's actual arrangement. |
| Bounded change | An owner-authorized effect limited by purpose, repository, paths, and validation claim. |
| Closure | Prior result accepted for an exact claim with a retrievable evidence locator. |
| Delta | The new work a continuation asks for after closure. |
| Invalidation boundary | Changes to inputs, assumptions, identity, or state that require revisiting prior evidence. |
| Checks not to repeat | Accepted checks reused while the invalidation boundary still holds. |
| Blocking finding | Review issue that prevents a proposed acceptance until resolved. |
| Nonblocking finding | Review issue that does not defeat the bounded accepted claim. |
| Handoff | Evidence-rich transfer record; it does not prove recipient comprehension or grant authority. |
| Workstream | Bounded research responsibility with a question, inputs, outputs, review, and acceptance route; not a branch, repository, agent, or session. |
| Dependency edge | Declared consumption of a specific input or evidence revision by an output. |
| Selective invalidation | Marking only evidence reachable from a changed dependency stale for its affected claim, while preserving unaffected evidence for its stated scope. |
| Coordination record | Human-readable history of decisions, dependency changes, handoffs, and continuation checkpoints; not an authority engine. |
| Harness | Software that retains or coordinates execution context across tasks or sessions; its logs and state do not replace project evidence or authority. |
| Lane | TOP-26-006 historical case-study terminology for a workstream, after the generic workstream concept; not a branch, repository, agent, or session. |
